Debugging Flaky Ember Tests

#programming #debugging #frontend #ember.js #testing

    ~ views | ~ words

    Sometimes tests can be reaaaally flaky and fail intermittently. It can be hard to chase these down, especially becuase it's not immediately clear how to reproduce an error. When I worked more with Ruby code, I loved how Rspec could run tests in a random order, but would tell you the seed value, so that if a random ordering revealed a breakage, you could use the seed value to run the exact same ordering again. I couldn't find an easy to way to do this in Qunit1, so I figured out a more hacky way to run tests enough times that I would hopefully reproduce my intermittent failures and be able to debug live.

    Here's how I did it:

    Run test suite multiple times

    I usually use ember server and then look at tests on the /tests page. This works for day-to-day development, but to really start from scratch it's better to run ember test. To do that, I used a good ole bash loop.

    for i in {1..20}; do ember test; done

    Turn off headless mode

    By default, ember test runs in headless Chrome. To debug and use Dev Tools, we want to use Chrome, but not in headless mode. To turn off headless, remove the --headless config in Testem config in testem.js.

    Open Dev Tools automatically

    Instead of futzing around with log statements, I wanted to just set a debugger and use Dev Tools. But when that Chrome window opens, it can be heard to get Dev Tools open right away. Automatically open them using the --auto-open-devtools-for-tabs flag in Testem config (testem.js), which is a Chrome CLI argument.

    Increase timeout values

    Pausing the debugger can keep the browser and the test process running for a long time and just exit while you're in the middle of debugging. You can increase the timeout to some large number by setting the browser_start_timeout and browser_disconnect_timeout values in Testem config.

    Alerts

    Of course when you're running your test suite 20 times back to back waiting for something to fail, you don't want to sit and stare at your computer. You'd much rather sit and stare at the TV while the computer is working. To get around that, you can play a beep when the test fails2:

    test("soemthing", (assert) => {
  const passed = actual === expected;
  if (!passed) {
    beep();
  }
  assert.ok(passed);
});

    In the end, my Testem config looks like this:

    module.exports = {
  framework: "qunit",
  test_page: "tests/index.html?hidepassed",
  disable_watching: true,
  launch_in_ci: ["Chrome"],
  launch_in_dev: ["Chrome"],
  browser_args: {
    Chrome: {
      mode: "ci",
      browser_start_timeout: 10000,
      browser_disconnect_timeout: 10000,
      args: [
        "--disable-gpu",
        // '--headless',
        "--auto-open-devtools-for-tabs",
        "--remote-debugging-port=9222",
        "--remote-debugging-address=0.0.0.0",
        "--no-sandbox",
        "--user-data-dir=/tmp",
        "--window-size=1440,900",
      ],
    },
  },
};
